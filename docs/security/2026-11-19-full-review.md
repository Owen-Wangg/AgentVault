## New findings

### N-1. Medium: public dashboard pages do work that grows with the sandbox, with no rate limit
- **Why medium:** one IP, staying inside its scenario-run limit, can slow every visitor's page loads until the nightly reset, and the product must stay up for judging until Jan 29, 2027. No money is at risk.
- **Where:**
  - `app/(dashboard)/agent-names.ts` (`getAgents`), called on the overview, feed, approvals and audit pages (`app/(dashboard)/page.tsx:16`, `feed/page.tsx:13`, `approvals/page.tsx:16`, `audit/page.tsx:39`). `src/server/dashboard/agents.ts:63` (`listAgents`) reads every agent in the workspace, with two correlated subqueries per agent, and no `LIMIT`. The whole map goes to the client as `agentNames`.
  - `src/server/dashboard/agents.ts:40-46` (`lastDecisions`, added since the last review) reads every `decision` event in the workspace with `DISTINCT ON (payload->>'agent_id')`. `src/server/db/schema.ts:304` gives `audit_events` only the `(workspace_id, seq)` primary key, so this reads the workspace's whole log.
  - `src/server/dashboard/audit.ts:42` with the new `?type=` filter (`app/(dashboard)/audit/page.tsx:21-23`): for a rare type, Postgres walks the workspace's events newest first until it finds 51 matches, which can be the whole log.
  - Dashboard pages are server components; nothing in `app/(dashboard)` or `proxy.ts` rate-limits them.
- **What:** each scenario run adds one agent (`src/server/scenarios/runner.ts:106`; the 25-agent cap in `manage.ts` applies only to `POST /api/v1/agents`) and up to about 36 decision events (the runaway scenario, `src/agents/scripted/scenarios.ts:168`). At the per-IP limit of 10 runs a minute (`scenarios/handler.ts`, `SCENARIO_RUN_LIMIT`), one IP adds about 14,000 agents and up to about 500,000 decision events to the current sandbox in a day. Every page load then serializes all agent names, and each agents page load reads every decision event. The per-IP and all-visitor caps bound how fast this grows but not what each page read costs. The nightly reset (`vercel.json`, `/api/cron/sandbox-reset`) starts a new sandbox, so the effect lasts at most a day.
- **Fix:** bound the reads, smallest first:
  - Build `agentNames` only for the agents on the page's events, or cap `listAgents` (for example the newest 200) for sandbox workspaces.
  - Add a partial index for `lastDecisions`, for example `CREATE INDEX ON audit_events (workspace_id, (payload->>'agent_id'), seq DESC) WHERE type = 'decision'`, and limit the query to the agents being listed.
  - Add an index on `audit_events (workspace_id, type, seq)` for the type filter.
  - Optionally count sandbox page renders per IP with `hitRateLimit`, as the API routes do.

### N-2. Low (latent): if GitHub sign-in is turned on, anyone can mint agent keys and write audit rows without limit
- **Why low:** the docs say sign-in is off on the hosted site (`docs/DEVPOST_STORY.md:14`), so today only the operator can make keys (`scripts/mcp-agent.ts`). Turning sign-in on would open this with no code change.
- **Where:** `src/server/agents/handlers.ts` (`handleCreateAgent`: any signed-in GitHub user, 25 agents each), `src/server/agents/manage.ts` (`updateEnvelope`; `callsPerMinute` is optional in `src/core/policy/envelope-wire.ts:23`, up to `MAX_CALLS_PER_MINUTE = 100_000`), `src/server/http/agent-route.ts` (`withAgent`: no per-agent or per-IP limit on `/api/v1/pay`, `/tool`, `/fetch`, or `/api/mcp`).
- **What:** a new user's agents have no sessions, so they can spend nothing (`guarded.ts`, the `!sessionRow` branch). But each request with a fresh `Idempotency-Key` still inserts an `idempotency` row and appends a `decision` event to the user's workspace chain. With `callsPerMinute` removed from the envelope, nothing freezes the agent. Twenty-five keys per GitHub account can fill the free Neon storage, which every workspace shares, including the sandbox.
- **Fix:** before turning sign-in on, add a per-agent fixed-window limit in `withAgent` with `hitRateLimit` (for example 120 a minute, keyed on the agent ID), and make `callsPerMinute` required with a ceiling such as 1,000.

### N-3. Low: a payout's destination read and an approved re-run's rail call can fail after commit and leave an approval marked `executed`
- **Why low:** no money moves on that path and the reservation stays counted, but the approval says it ran when it didn't, and the reconciler then has to prove the payout never happened.
- **Where:** `src/server/payments/guarded.ts:695` (`payoutDestination` runs after the decision transaction committed, outside the `try`); `src/server/approvals/service.ts` (`actOnApproval` commits `status = executed`, then calls `executeGuarded`).
- **What:** if the destination read throws (database blip), `executeGuarded` throws before the rail call and before any `rail_result` is written. The route returns 503. The approval row already says `executed`, the decision event says `allow`, and the reservation stays `reserved` until the reconciler's Stripe or PayPal lookup proves no transfer exists. A person reading the inbox sees an executed approval with no rail result. This matches the comment at `:694-695`, and it fails closed for money; the gap is in what the audit trail and the approval show.
- **Fix:** move `payoutDestination` inside the `try` and treat a thrown read as `{ ok: false, code: "RAIL_REJECTED" }` (nothing was sent), so `recordOutcome` writes a `failed` rail result and releases the reservation. Or read the destination inside the decision transaction and pass it through `Pending`, keeping PO-4's "read when it runs" by reading it under the envelope lock just before commit.

### N-4. Low: two scenario runs that send the same `run_id` collide on the per-run supplier's name
- **Why low:** the second run fails closed with a 503; it can't redirect another run's payout.
- **Where:** `src/server/scenarios/handler.ts` (`RunBodySchema`: `run_id` is any client UUID), `src/server/scenarios/runner.ts:124` (`runPayeeName` uses 8 hex characters of `sha256(run_id)`), `src/server/db/schema.ts:183` (unique `(workspace_id, name)` on vendors).
- **What:** PO-23 gives each hijack run its own supplier so one run's approved payee change can't redirect another run's payout. A visitor who resends a `run_id` (or, at about 65,000 hijack runs in one sandbox day, a random 32-bit collision) makes the vendor insert fail and the run return 503. The unique index is what keeps this safe.
- **Fix:** derive the supplier name from a server-generated value (for example the new agent ID), or use 16 hex characters and reject a `run_id` already present in a `scenario_started` event.

### N-5. Low: the CSP and the proxy matcher leave a few HTML responses without a page policy
- **Why low:** none of these responses renders untrusted input or runs script, so the CSP here is defense in depth.
- **Where:** `proxy.ts:52` excludes `vendor/` and `api/`; `proxy.ts:53-57` skips requests with `next-router-prefetch` or `purpose: prefetch`; `src/server/vendor/weather.ts:54` (`customPaywallHtml` for browsers on `/vendor/api/weather`).
- **What:** the vendor docs and invoice set their own strict CSP (`src/server/vendor/pages.ts`, `STATIC_PAGE_HEADERS`), but the x402 paywall page that `withX402` serves to browsers gets only the `next.config.ts` headers, with no CSP. It is a static string with a price from code. Page prefetches skip the nonce CSP as the Next.js docs recommend; a browser that caches a prefetched document and later shows it would show it without the CSP. HSTS has no `includeSubDomains` (`next.config.ts`), which is normal on a `vercel.app` subdomain.
- **Fix:** add `/vendor/api/:path*` to `next.config.ts` with `Content-Security-Policy: default-src 'none'; frame-ancestors 'none'`. The prefetch exclusion can stay.

## Checks that found nothing

- **Money.** No `parseFloat`, `.toFixed()`, `Math.*` or `Number(...)` on amounts in `src/`, `app/` or `scripts/` outside test fixtures; search hits are counts, timestamps and Stripe integer JSON. `toRailUnits` is called only in `src/rails/**`, `src/core/money` and the operator script `connect-setup.ts`; the server counts with `chargeableMicros` (`guarded.ts`). Wire amounts are `MicrosSchema` strings.
- **Payment flow order.** `runGuardedRequest` (`guarded.ts:673`) runs `decideGuarded` in one transaction: envelope `FOR UPDATE` (`:295`), idempotency claim, frozen flag read after the lock, state loads, `evaluate()`, refund check, `decision` event (`:433`), freeze on `VELOCITY_EXCEEDED`, approval on hold, reservation on allow. The rail call (`executeGuarded`, `:680`) runs after commit, and `recordOutcome` writes `rail_result` in a second transaction. Authentication comes first (`withAgent`), bodies are `strictObject` with a 16 KB cap, and `approval:` keys are reserved for re-runs.
- **Fail closed and precedence.** Errors in steps 1 to 7 roll back and return 503 with a correlation ID. `combine()` denies on any non-hold code, including unknown ones (`src/core/policy/evaluate.ts:33`). `withoutApproved` drops only hold codes. The advisory score can only add `ADVISORY_DRIFT`, and the re-run reuses the stored score.
- **Taint and scope.** Taint moves only from unset to set (`src/core/taint/session.ts`), under a row lock, before the body is returned. A redirect chain is trusted only if every hop is (`proxy.ts`, `labelChain`), and trust entries match exact origin plus whole path segments (`src/core/taint/label.ts`). All five high-privilege tools are hard-coded (`src/core/taint/rules.ts`) and flagged in the registry. Sessions are created only by server code (runner, testnet handler, MCP provisioning), so an agent can't start a clean session. Vendor categories come from the registry.
- **SSRF.** `safeFetch` allows https only (http to localhost in development only), refuses credentials, checks every resolved address against IPv4 special ranges and IPv6 outside global unicast, pins the checked addresses for the connection, re-checks each of up to 3 redirects, and caps the body at 1 MB after decompression and the fetch at 10 s (`src/server/fetch/fetcher.ts`, `ip.ts`). The live agent's `fetch_url` is limited to the app's origin (`src/agents/gemini/tools.ts`).
- **Approvals.** `withHuman` refuses any `Authorization` header and cross-site POSTs before opening the database (`src/server/approvals/handlers.ts`). Approve-once is the `status = 'pending' AND expires_at > now` update; expiry runs on every list and action with one event each; the re-run locks the envelope first, uses `approval:<id>`, checks the agent's workspace and revocation, and fails its recheck on any deny or unapproved hold. - **Audit log.** Triggers block `UPDATE`, `DELETE` and `TRUNCATE` (`migrations/0001`). Appends lock the head, check its MAC in constant time, and re-sign it (`append.ts`, `chain.ts`).
