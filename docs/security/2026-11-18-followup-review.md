## New findings

### N7. Low: GitHub tokens stored before the fix are still in the database
- **Why low:** the tokens are unused by the app and are only reachable through a database leak, but they are real GitHub tokens.
- **Where:** `src/server/auth/adapter.ts:9-21` (only wraps `linkAccount`); migrations `0000` to `0006` contain no statement that clears the `account` columns (`0000_initial_schema.sql`, `account` table).
- **What:** the wrapper stops new rows from holding tokens. Rows written by earlier sign-ins keep their `access_token`, `refresh_token` and `id_token`, because Auth.js calls `linkAccount` only when an account is first linked.
- **Fix:** run once against each database: `UPDATE account SET access_token = NULL, refresh_token = NULL, id_token = NULL;` (as a documented operator step or a new migration; do not edit applied migrations). Users can also revoke the app's grant in their GitHub settings.

### N6. Low (latent): refunds are still not tied to a payment this workspace made
This is F6, unchanged. `src/server/tools/tool-handler.ts:~26` (`Ref` accepts any `[A-Za-z0-9_-]{1,255}`), `guarded.ts:288-290` (only checks presence), `src/rails/stripe-mpp/adapter.ts:80` (`^pi_\w+$`). An agent allowed `stripe.refund` can name any PaymentIntent in the platform's Stripe test account. The only users are non-sandbox workspaces with `RAIL_MODE=real`, and a tainted session is held. **Fix:** as in F6: before reserving, require a settled `rail_result` of this workspace with `rail_ref` equal to `payment_ref`, and cap the refund at that payment's settled amount minus earlier refunds.

### N2. Low: early denials still skip the velocity check, and the audit log takes unbounded agent-chosen text
- **Where:** `guarded.ts:286-296` (unknown tool, refund without ref, payee without destination, bad session), `:154` (`loadCallsLastMinute`, called only in the evaluated branch), `src/server/tools/tool-handler.ts` (`UNKNOWN_TOOL_ARGS`, `tool` up to 100 characters, `vendor` up to 200).
- **What:** the frozen case is fixed, but a request refused before `evaluate()` never gets `VELOCITY_EXCEEDED`, so a flood of unknown-tool calls never freezes the agent. Each one still writes a `decision` event holding the agent's `tool` and `vendor` strings into the append-only log, plus an idempotency row. No per-agent throttle exists in the files I read. A holder of a valid key can grow the log without limit (about 300 bytes of its own text per request), which also feeds the storage limit in N4.
- **Fix:** run the velocity check before the early branches (load `callsLastMinute` and compare with the envelope's `callsPerMinute`), or send the unknown-tool case through `evaluate()` with a placeholder non-privileged tool. Alternatively, rate-limit per agent in `withAgent`.

### N3. Low: the new all-visitor limits can be used to lock other visitors out
- **Where:** `src/server/http/rate-limit.ts` (`hitRateLimit` increments on every call, including rejected ones), `src/server/testnet/handler.ts:84-86` (20 a day, 6 a minute, all visitors), `scenarios/handler.ts:151`, `events/handler.ts:123`.
- **What:** a caller with several IPs can burn a shared bucket. For the testnet button, 10 IPs at 2 presses an hour use the day's 20 and every later visitor gets `TESTNET_QUOTA_USED`. The same applies to scenario runs (60 a minute) and sandbox streams (120 a minute), which would stop the public demo from loading. No money is at risk, since the demo agent's envelope caps spend. The demo has to stay up for judging, so this is an availability risk.
- **Fix:** accept it and monitor (`pnpm ops:check` already reports testnet counts). The handlers already return before the shared bucket when the per-IP limit fails, so one IP cannot take more than its own share; the remaining exposure is many IPs, which only a CAPTCHA or an upstream (Vercel firewall) rule would close.

### N4. Low: remaining F4 items, plus connection use of streams
- **Where:** `src/server/audit/append.ts:100` (`loadChain` loads the whole chain; unchanged), `src/server/events/handler.ts:45`, `src/server/scenarios/handler.ts:77`.
- **What:** `POST /api/v1/audit/verify` is still unpaginated. At 120 stream opens a minute and 55 seconds per stream, about 110 streams can be open at once, each holding a database connection, which is more than a free Neon plan is likely to allow. At 60 runs a minute and up to 100 requests each, a run flood is up to 6,000 requests a minute. I did not re-read `/vendor/api/*` (no rate limit in the first review) or `POST /api/v1/agents` (no cap), and no hardening commit touched them, so I take them as unchanged.
- **Fix:** lower `SANDBOX_STREAM_TOTAL_LIMIT` to what the database connection limit allows, page `loadChain`, and rate-limit the vendor routes.

### N5. Low: the CSP is report-only, so it blocks nothing, and `script-src` allows inline scripts
- **Where:** `next.config.ts:24` (`Content-Security-Policy-Report-Only`), `:12` (`script-src 'self' 'unsafe-inline'`), `app/security-headers.test.ts` (asserts the enforcing header is absent).
- **What:** clickjacking is covered by `X-Frame-Options: DENY` (`:27`). XSS defense is the absence of HTML sinks, not the CSP. Once enforced with `'unsafe-inline'` it would add little for scripts. I found no sink in the first review.
- **Fix:** keep the report-only phase, then move to a nonce-based `script-src` through middleware and enforce it. Add `Permissions-Policy` if wanted. Update the test with the change.

### N8. Low: dependency state after the commits
- **Where:** `package.json` dev dependencies `@types/node ^22.20.5`, `@types/react ^19.3.0`, `@types/react-dom ^19.3.0`, `eslint ^10.14.0`, `fast-check ^4.10.2`, `tsx ^4.23.15`, `vitest ^5.1.0`; `next-auth 5.0.0-beta.32`; `pnpm-workspace.yaml:2` (`esbuild: true`); `react-is`.

Auth runs on a beta. `esbuild` is still allowed to run an install script without a recorded reason, while `protobufjs: false` has one. `react-is` is not imported in the files I searched earlier. Advisory data was not checked.

### N9. Low: `mpp:validate` runs unpinned remote code with a Stripe key in its environment
- **Where:** `scripts/mpp-validate.ts:22` (sets `MPPX_STRIPE_SECRET_KEY` from `STRIPE_SECRET_KEY`), `:24` (`npx --yes mppx@latest validate`, `shell: true` on Windows).
- **What:** whatever the registry serves as `mppx@latest` runs with the test key. The key is checked to be `sk_test_` first (`checkStripeEnv`) and the target URL is validated against a strict pattern (`:15`) before it reaches the shell, so the exposure is a test-mode key only. A supply-chain issue with that package would take the key.
- **Fix:** run the pinned local copy (`pnpm exec mppx validate <origin>`; `mppx` is pinned at 0.19.0 in `package.json`) instead of `@latest`.

### N10. Info: smaller points in the newly read code
- **Reconciler and Stripe or PayPal lookups do not compare amount or destination.** `src/rails/stripe-mpp/payouts.ts` (`lookup`) marks a reservation settled for the one transfer found under `transfer_group = <reservation id>`, and `src/rails/paypal/adapter.ts` (`lookup`, `readBatch` without `expected`) does the same for the batch whose `sender_item_id` matches. The reconciler holds no request to compare with. The grouping key is the reservation id the server generated, so a mismatch would need someone with the platform's Stripe or PayPal keys. `payout()` itself does compare amount, currency, destination and group (`payouts.ts` after the transfer; `paypal/adapter.ts` `readBatch` with `expected`).
- **Sandbox reservations with an unknown outcome stay reserved until the nightly reset.** `src/rails/mock.ts` `lookup` returns `unknown` for a key it never recorded, and its records live in one process's memory. Only the sandbox is affected, and it counts toward that sandbox's caps.
- **`authenticateAgent`'s `timingSafeEqual` is a no-op.** `src/server/auth/agent-keys.ts` compares the stored hash with the hash it looked up by equality, so they are always equal. The real protection is the lookup of a SHA-256 of a 256-bit key through a unique index, which leaks nothing useful. Revocation is checked after (`revokedAt`). No change needed; the comment overstates what the compare adds.
- **PayPal receiver check is stricter in code than in the database.** Migration `0004` allows any email domain in `vendors.paypal_receiver`; the sandbox-domain rule is enforced in `src/rails/config.ts` (`SANDBOX_RECEIVER`) and the adapter's `checkDestination`, on every payout. It fails closed at payout time. Aligning the check constraint would add a second layer.
- **Other unbounded reads are from fixed hosts.** `src/rails/x402/chain.ts:84` (`response.json()` from the constant RPC URL), `src/rails/paypal/adapter.ts` `readJson`, and `src/rails/stripe-mpp/stripe-api.ts:103` do not cap body size, but their hosts are constants, not vendor-controlled.
- **Operator scripts print secrets by design.** `scripts/wallet-new.ts` prints a new testnet private key, and `scripts/mcp-agent.ts` prints a new agent API key once. Both are documented in the file headers.
- **Embedded instructions.** I found none in the files I read this pass, and I did not re-read `app/vendor/**` or `src/server/vendor/pages.ts`.

## Checks that found nothing

- **Money.** In the files I read: no `parseFloat`, `.toFixed()`, `Math.*` on amounts, or `number`-typed amount fields. PayPal amounts are built from integer cents (`paypal/adapter.ts` `paypalAmount`) and parsed with a regex (`parsePayPalAmount`). Rail JSON amounts (`Transfer.amount`, `max_amount`) are parsed as integers and converted with `BigInt` before comparison. Conversion calls (`toRailUnits`) appear in `src/rails/**` and in the operator script `connect-setup.ts` (the `--fund` option); the server uses `chargeableMicros` (`guarded.ts`). `scripts/ops-check.ts` uses `Number()` on a day count, not money.
- **Rail configuration.** `src/rails/config.ts` refuses `sk_live_` and `rk_live_` in every mode, requires `sk_test_` and `profile_test_` in real mode, forces the network to `eip155:84532`, forces `PAYPAL_ENV=sandbox` and sandbox receiver domains, refuses the zero address and `.env.example` placeholders, and requires different supplier and attacker receivers and different vendor and agent wallets. Messages name variables, never values. `pay-handler.ts` validates this per request through `serverRailFor`. PayPal calls use the constant `PAYPAL_SANDBOX_API` and re-check `sandboxOnly()` on every call.
- **PayPal and Stripe payouts.** One reservation maps to one transfer or batch through idempotency keys; any outcome after the request was sent that does not prove a result is `unknown` and keeps the reservation; live-mode objects are rejected; the destination is read from the registry when the payout runs (`guarded.ts:497`); the amount and destination of the returned object are compared with the request.
- **Reconciler.** Calls only `lookup()`, never `execute()`, `refund()` or `payout()`; resolves only reservations still `reserved` under `FOR UPDATE SKIP LOCKED`; releases only on a `failed` lookup; writes an audit event before changing the reservation; a failed or unknown lookup changes nothing. The cron routes use `hasCronSecret` (`src/server/cron/auth.ts`), which hashes both sides and compares with `timingSafeEqual`, and return 503 when `CRON_SECRET` is missing.
- **Pay and tool routes.** `PayBodySchema` is `strictObject` with a UUID session, an enum of pay tools and `MicrosSchema` amounts. Each registered tool has a strict argument schema; own-property lookups guard against `__proto__`; payment tools sent to `/api/v1/tool` get 400. Registry flags match the five high-privilege tools in the standard.
- **Testnet workspace.** The handler uses `withHuman` (bearer headers and cross-site requests refused before the database opens), accepts only an empty body, checks per-IP and all-visitor limits before creating anything, fixes vendor, tool and amount in code, and the demo agent has an unusable key hash, a $0.01 per-payment and $0.05 daily envelope and a task with no high-privilege tool (`testnet/workspace.ts`). `testnetRailReady` never reveals which variable failed. `scripts/testnet-setup.ts` accepts only an https origin (or localhost) with no path.
- **Database.** Parameterized queries throughout. Migrations: audit append-only triggers (`0001`), check constraints for reservation amounts, vendor payment URLs on the vendor's origin (`0003`), destination formats (`0004`), `rail_ref` length (`0005`), one public testnet workspace and never a sandbox (`0006`). `envelope-json.ts` parses stored envelopes with strict schemas, rejects `__proto__`, and throws on anything malformed. No migration or script contains a secret.
- **Scripts.** `e2e.ts` builds its throwaway database name from hex digits only and refuses to use `DATABASE_URL`; `guard-shell.mjs` fails closed on unreadable input; `load-env.ts` lets shell variables win and prints nothing; no other `exec`, `eval` or `shell: true` use beyond `mpp-validate.ts` and `e2e.ts` (whose arguments are the script's own).
- **Approvals and human routes.** `withHuman` refuses any `authorization` header and cross-site requests before opening the database (`approvals/handlers.ts`); the events route does the same for bearer headers. Unchanged by the commits.
- **Regressions from the hardening commits.** The frozen-agent change adds `AGENT_FROZEN` ahead of the original reasons and still returns 403 with a stored response. The URL redaction changes only what is written, not the taint decision (`afterFetch` still receives a non-null URL). The IP change leaves routes working off Vercel with one shared bucket. The new limits are checked after the per-IP one and before any state is created. I found no path where a change makes a deny, hold or taint check weaker.
