# Kiro Development Log

Raw notes for the Devpost "How Kiro was used" write-up. The `devlog` hook (Stop trigger) appends to this file.

## 2026-11-13

- **Research and planning with Kiro.** Kiro read the Kiroween 2026 Devpost overview, Stripe's machine payments docs (MPP, x402, Shared Payment Tokens), the Coinbase CDP x402 seller quickstart, Gemini rate-limit docs, and Kiro's own hooks and steering docs. The Devpost Rules page was blocked to fetching, so the judging text was pasted in manually.
- **Research changed the design.** Stripe's docs show MPP sessions charge in sub-cent increments, so integer cents could not represent the core threat (micro-payment drain). The money unit became `bigint` micros (1 USD = 1,000,000, matching USDC's 6 decimals). Stripe's SPT docs confirmed Canada supports SPTs and offer a sandbox test helper, which made a real Stripe test-mode rail possible from a Canadian account.
- **Spec-driven development.** Created 7 feature specs in Kiro's layout (`.kiro/specs/<feature>/requirements|design|tasks.md`) with EARS acceptance criteria and IDs (MON, ENV, PXY, AUD, HITL, TAINT, INT, RAIL, TEL, UI, AGT, MCP). Each design doc lists numbered correctness properties that become fast-check property tests.
- **Writing the specs caught design bugs before any code:**
  - Banker's rounding could round a debit down, which favors the agent. Replaced it with directional rounding (debits round up, credits round down).
  - Holding a database row lock during a blockchain payment would block every other request for that agent for seconds. Replaced it with spend reservations committed before the rail call.
  - The prompt-injection demo task must allow `stripe.refund`. Otherwise intent scope denies the refund first, and the demo would never show the taint defense.
  - The proxied fetch endpoint needed SSRF protection (private IP ranges, redirects, cloud metadata address).
- **Steering.** Foundation files (`product.md`, `tech.md`, `structure.md`) plus `security-standards.md` (always included), `money-arithmetic.md` and `testing-standards.md` (fileMatch), and `validate-mpp.md` (manual slash command, since the IDE no longer creates Manual hooks).
- **Hooks.** 7 hooks: test-on-save, no-float-money, spec-trace, post-task-verify, devlog, guard-shell (PreToolUse; AgentVault's own taint idea applied to Kiro's shell access), and kiro-dir-guard (protects against the `.gitignore` disqualification rule). Five start disabled until project setup (Phase 2) creates their scripts.

## 2026-11-14

A rail timeout is now recorded as `unknown` and the reservation stays counted until a reconciler resolves it with a read-only `lookup()`. Only a confirmed failure releases money.

  - A 0.01 USDC rail minimum in steering would have rejected the sandbox's $0.0015 payment.
  - Refunds round down at the rail, so the envelope now counts the full requested refund (MON-11).
  - The scenario seeds now make each demo produce exactly one intended reason code.
- **Steering and planning.** Added an always-included `git-commits.md` steering file for commit format. Added `docs/PLAN.md` with dependency-ordered phases and a scope-cut order. "Task" now always means a `tasks.md` entry, which matches Kiro's task UI.

  - Kiro's hook docs (checked with the `introspect` subagent) showed that `timeout` belongs on the hook, not the action. All hook files were fixed.
  - The `.kiro` gitignore check first reported false matches. Git's `check-ignore` misreports paths that end in a slash, so the script now passes folders without one.

## 2026-11-16
- **Phase 4: policy engine** (money-and-policy-core tasks 3–6). Reason codes, strict Zod input schemas, six envelope rules, `evaluate()` and `combine()`, and `pnpm demo:policy`, with 100 new tests (263 total). Taint and intent rules are stubs returning `[]` until Phase 7.
  - **Property test catching a fail-open bug (write-up demo).** The generators deliberately include vendor names like `__proto__` and `constructor`. Property 5 ("allowed spend never exceeds any cap over a request sequence") failed with seed `-792056920` and shrank to one 1-micro payment to vendor `__proto__`, whose day cap was 0, being allowed. Cause: Zod's `z.record` silently skips an own `__proto__` key, so the limit vanished during parsing without being validated or enforced. The ENV-11 property found the same thing from another angle (seed `942873590`: a calls-per-minute limit of 0 under `__proto__` was ignored). Fix: limit maps keyed by `__proto__` now fail the schema, so the request is denied with `INVALID_REQUEST`. The shrunk counterexample is kept as a regression test.
  - A compile-time check that every `EvaluateInput` value passes the schema failed on the first run: the types use `readonly string[]` and Zod's arrays are mutable. The schema arrays are now `.readonly()`.
  - Property 5 also failed once on a bug in its own simulator (it selected history by timestamp, and two steps can share one), not in the engine. It now selects by position.
  - Decisions made in this phase: `NEEDS_APPROVAL` is added only when no deny rule fired (ENV-8's "passes all deny rules"); vendor- and tool-level calls-per-minute limits are checked against the agent's total call count, because window state has no per-vendor count, which can only deny more; `combine()` denies on any code that isn't a known hold reason, so an unknown code fails closed; an envelope or session loaded for a different agent or session is `INVALID_REQUEST`.
  - The runaway, normal, and injection scenarios' envelope parts are pinned to their exact demo-agents reason lists in unit tests.

## 2026-11-18
- **Phase 5: audit log foundation** (audit-and-approvals tasks 1–3). Canonical JSON and hash-chain math in `src/core/audit`, the Drizzle schema with append-only triggers, `appendEvent()` and `verifyChain()`, the seeded sandbox with its reset and cron route, and `pnpm audit:verify`, with 133 new tests (396 total).
  - **A design gap found while writing `appendEvent`.** The design locked the head and extended it, but never checked the head's MAC first. An attacker with database access could delete rows from the end, roll the head back to match without the key, and wait: the next normal append would re-sign the forged head, and the chain would verify again. `appendEvent` now refuses to extend a head with a bad MAC, and an integration test rolls a head back and checks that the next append fails.
  - **The Phase 4 `__proto__` lesson applied again.** Envelope limits are read back from jsonb, and `z.record` would silently drop a `__proto__` key there too. The decoder rejects it, with a test.
  - **Independent test vectors.** The canonical strings in `vectors.json` were typed by hand and hashed with `node:crypto`, not with the code under test, so the vectors check the encoder rather than repeat it. One vector covers UTF-16 key order, where an emoji key sorts before `\uffff`.
  - **Integration tests without Docker.** This machine has no Docker or Postgres, so integration tests fall back to PGlite (Postgres compiled to WebAssembly, in memory) when `DATABASE_URL_TEST` isn't set. The triggers, plpgsql, `FOR UPDATE`, and advisory locks all run on it. The testing-standards steering file now says so; concurrency tests still need a real server.
  - Mutation checks: removing the head MAC check in `appendEvent`, the agent revocation on retire, the tail check, the link check, or the workspace check in `verify` each makes a test fail. The property tests found no bugs in this phase.
  - The production build failed because the database client resolved the migrations folder with `import.meta.url`, which Next.js tried to bundle into the cron route. Migrations moved to their own module that only scripts and tests import.
  - pnpm's minimum release age policy blocked `@neondatabase/serverless` 1.2.1, published the day before. It's pinned to 1.2.0 instead of adding an exception.
  - `verify()` now takes the workspace ID (design doc updated), so rows or a head copied from another workspace fail. It checks `seq` before the link, so a deleted row is reported at its own `seq`.
- **Neon setup and the first run on real Postgres.** The database is in AWS us-west-2 (Oregon), close to Vancouver where development happens, so Vercel functions must run in `pdx1` (noted in `tech.md`). Migrations, seeding, a sandbox reset, and `pnpm audit:verify` all worked on Neon. The integration tests then ran against a Neon `test` branch: all tests passed, but the run reported 3 uncaught errors. Dropping each throwaway test database `WITH (FORCE)` ended connections that were still closing, and no pool had an `error` listener, so Node treated it as an uncaught exception. Vitest printed the whole driver error, which references the client and its connection password. The password was rotated on both branches. Every pool and client now logs only the error code and message, which also matters in production because Neon closes idle connections when it scales to zero. A clean rerun passed all 399 tests with no errors.

Origin labels, the taint rule, and sticky session taint in `src/core/taint`; intent scope rules in `src/core/intent`; both wired into `evaluate()`; the SSRF-safe fetcher and `POST /api/v1/fetch`; `POST /api/v1/tool` with refunds running on the rail; and the demo vendor pages, with 231 new tests (753 total).

  - **A weak property, found by breaking the code on purpose.** Property 1's first form only checked that a privileged request after a taint is never `allow`. Most generated inputs are already denied by some other rule, so that check alone would pass even with a broken taint rule. The test also asserts `HELD_TAINTED` is present, which is what caught the mutation (taint rule trusting only the registry's flag: seed `-761266326`, shrunk to a `stripe.refund` with `privileged: false`).   - **Design gaps closed while writing the code:**
    - The design gave `taintRules` a `ToolDef`, but `EvaluateInput` had no tool flag. It now has `tool`, and the schema rejects a definition whose name differs from `request.tool`, so a refund can't borrow `x402.pay`'s unprivileged flag. The four tools named in the security standards count as high-privilege even if a registry entry forgets the flag.

The connection now uses only the checked addresses. A test listens on 127.0.0.2 only and passes only if the pinned address is used.

    - The Phase 4 `__proto__` lesson again: tool `args` aren't parsed with `z.record`, which would silently drop an own `__proto__` key. Each tool's strict schema checks the raw value.
    - A refund's `payment_ref` wasn't in the idempotency hash, so the same key with a different payment would have replayed the first refund's result. Tool `args` are now in the hash, the decision event, and the approval, so Phase 8's re-run gets the reference back.

## 2026-11-23
- **Phase 8: approvals and the reconciler** (audit-and-approvals tasks 7–9). `approvedHoldReasons` in `evaluate()`; the approvals service with `GET /api/v1/approvals`, `POST /api/v1/approvals/:id`, and `POST /api/v1/agents/:id/unfreeze`; a model-based test of the approval state machine; and the reconciler with its after-request trigger, daily cron route, and `pnpm reconcile`, with 55 new tests (808 total).
  - **The injection scenario now finishes (write-up demo).** The poisoned-docs refund held with `HELD_TAINTED, NEEDS_APPROVAL` is approved anonymously in the sandbox and re-runs under the key `approval:<id>`: the refund runs once on the rail with its `payment_ref`, the approval becomes `executed`, and the original key still replays the hold. If the envelope stops allowing `stripe.refund` before the approval, the same approve ends in `failed_recheck` with `TOOL_NOT_ALLOWED` and nothing runs (TAINT-9).
  - **The model-based test first missed an off-by-one in expiry.** A deliberate mutation (expire only after `expires_at`, approve at exactly `expires_at`) passed two full runs of 20 cases, because random clock advances almost never landed an approval exactly on its expiry, and many runs never created an approval. Each run now starts with two held approvals, and a command jumps the clock to an approval's expiry give or take 1 ms. The same mutation then fails on the first run and shrinks to two commands, `advance(15 min), read` (seed `-2124937188`).
  - **Property 6 catches a reconciler that releases money without proof.** With "unknown" treated as a failure, it shrinks to: the adapter throws mid-payment, then a reconcile run 10 minutes later (seed `2017577166`). The property checks that each release matches a failure the rail itself reported, not just that some `failed` event exists. Without the `SKIP LOCKED` re-check, 4 concurrent runs wrote 24 reconciled results for 6 reservations.
  - **Design gaps closed while writing the code:**
    - Lock order. The pay flow locks the envelope, then the audit head, then (on a velocity freeze) the agent row. An approve that appended `approval_decided` before re-running, or an unfreeze that updated the agent row first, could deadlock with a concurrent pay request from the same agent. Both now lock the envelope first.
    - An agent could send its own request with the key `approval:<id>` (the ID is in the hold response) before the human approves, so the approval would replay the agent's stored result. Agent routes now reject keys with that prefix, and a re-run whose key is already claimed fails closed.
    - With the `pending → approved` update in its own transaction, a database error during the re-run would leave the approval stuck in `approved` with nothing run. The update, the re-run's decision, and the final status now commit together, so a failure leaves it `pending`.
    - HITL-3 says to mark a failed recheck "with those reasons", but the table had nowhere to keep them apart from the original hold reasons. Migration 0002 adds `recheck_reasons` and `rerun_decision_seq`.
    - Every test's fake clock starts in the same minute, so tests shared one sandbox rate-limit window and would have started failing with 429 as tests were added.
  - Mutation checks, each making a test fail: approvals that also drop deny reasons (the caps property found an approval lifting a $0 hourly cap, seed `98332974`); approving without the `status = 'pending'` condition (the second approve got 503 from the derived-key guard, not a second payment); approving every hold code instead of the ones the request was held for; expiry without the `pending` condition (duplicate `approval_expired` events).
  - Decisions: approved hold reasons match by code, not detail. Any `Authorization` header on a human-only route is 403 before the database is opened, so there's no key lookup to time. Sandbox actions are limited to 30 per IP per minute per action. `vercel.json` pins functions to `pdx1` and schedules the reconciler daily; the sandbox reset entry comes in Phase 18. Migration 0002 is applied in tests but not yet on the main Neon branch.

## 2026-11-24
- **Phase 9: the live event stream** (telemetry-dashboard task 1). `GET /api/v1/events` streams a workspace's audit events over SSE with `seq` as the event ID. The loop (`pumpEvents()`) has its event source and clock injected, and the handler handles scoping and rate limiting. 21 new tests (829 total).
  - **The coverage check caught weak generators before any bug did.** Property 1 counts how often a client drops right after a full batch while more events are waiting, and how often an event commits during a poll after the poll's snapshot. The first generators reached the batch-boundary case in 9.9% of runs, under the 10% floor, so the test failed. Bursty commits and a backlog of events before the first connection raised it to about 32%, with commits during polls in about 47%.
  - **Why a `seq > cursor` poll can't skip an event.** `appendEvent` holds the workspace's head lock until commit, so events commit in `seq` order, and one query that sees `seq = n` sees every lower `seq`. A Neon-only test holds an append open, checks that a poll sees neither it nor a second append queued behind it, then sees both after the commit. With the head lock removed (mutation), that test and the handler property fail with duplicate-`seq` errors.
  - **A design gap closed: reconnecting to the wrong chain.** Each sandbox reset starts a new workspace whose `seq` restarts at 1. A dashboard that reconnected with `Last-Event-ID: 57` and was resolved to the new sandbox would have skipped its first 57 events. Clients now name the workspace with `?workspace_id=`, and each connection starts with an id-less `workspace` message (`workspace_id`, `sandbox`, `retired`) that doesn't move the browser's last event ID. Retired sandboxes stay readable, and `retired: true` tells the client to reload.
  - Mutation checks, each making a test fail: `id` only on the last event of a batch (seed `1166052875`, shrunk to a client that drops after one event of a two-event batch and gets seq 1 twice); fetching one extra row to detect more and taking the cursor from it (seed `-698122820`, seq 2 skipped at a batch boundary); resuming at `Last-Event-ID + 1` (seed `-2142329604`); no heartbeat (TEL-3); no deadline (TEL-4); `seq >= cursor` in SQL; no workspace filter; no owner check; no bearer check.
  - The fake client first ignored events without an `id` line, so the id-only-on-last mutation looked like lost events instead of the duplicates a real EventSource would see. It now delivers every event and lets only `id` lines move the last event ID, as the SSE spec does.
  - Decisions: a heartbeat after 10 s idle keeps the gap under 15 s even with a 1 s poll and a slow query. The stream starts no poll after 55 s, so it ends before the 60 s `maxDuration`, and a unit test checks that the route's literal matches the stream's constant. A database error mid-stream ends the stream, and the browser reconnects from its last ID. Any `Authorization` header is 403, as on the approvals routes. Sandbox streams count toward a 30 per minute per-IP limit, because each holds a function for up to 55 s. `defaultWorkspace()` is shared with the approvals list. The integration version of property 1 runs 8 cases, because each case makes dozens of round trips to Neon. `pnpm verify` takes 51 to 66 s.
